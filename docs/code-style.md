# MyDSH 代码规范

本规范适用于 MyDSH 自有代码：

- `src/`
- `scripts/`
- `tests/`
- `packages/` 中不在 `docs/upstream/dsh/manifest.json` 里的模块，以及 `packages/preset/agent-presets` 中 MyDSH 新增的 `coding-tools.js`、`patch-format.js`

移植自 DeepSeek Harness 的模块和 `vendor/` 保持上游写法，不按本规范改写，避免升级时产生无关差异。

规范的目标只有一个：让第一次接触这段代码的人，不用猜就能看懂它做什么、为什么这样做、出错时会怎样。逻辑正确但难以阅读的代码，同样需要修改。

## 自动门禁

`pnpm run check` 包含下列检查，CI 也会执行。不合规的改动不能合入。

| 检查 | 命令 | 约束 |
| --- | --- | --- |
| 格式 | `pnpm run format:check` | 统一由 Prettier 排版，提交前运行 `pnpm run format` |
| 规模与结构 | `pnpm run lint` | 见下文“规模与结构” |
| 注释 | `pnpm run verify:comments` | 每个文件有说明职责的文件头，每个导出声明有中文 JSDoc |
| 豁免清单 | `pnpm run verify:lint-debt` | 规模类 lint 豁免中的文件必须仍然违反对应规则 |

尚未整理的旧代码暂时豁免，登记在两份清单中：规模类规则登记在 `.oxlintrc.json` 末尾、逐个列出文件路径的 `overrides` 里，注释要求登记在 `scripts/comment-debt.json` 里。这两份是只减不增的待整理清单：

- 不得为新代码添加豁免。
- 文件整理达标后，必须从清单中删除。`verify:lint-debt` 和 `verify:comments` 发现清单中的文件已经达标或已被删除时，会报告失败并指出需要删除的条目。

## 格式

- 由 Prettier 统一排版：行宽 100，不写分号，字符串使用单引号，多行结构保留尾随逗号，单参数箭头函数不加括号。配置见 `.prettierrc`。
- 一行只写一条语句。不要用分号或逗号把多个动作挤在一行里。
- 长条件拆成命名清楚的中间变量或小函数，不要靠换行硬撑一个超长表达式。
- 拼接 CSS 类名时，使用 renderer 的类名工具函数，不要在模板字符串里嵌套三元表达式。

## 规模与结构

| 项目 | 上限 |
| --- | --- |
| 文件 | 600 行（不计空行和注释） |
| `.ts` 函数 | 80 行 |
| `.tsx` 组件或函数 | 150 行 |
| 嵌套深度 | 4 层 |
| 参数个数 | 4 个；更多时改用一个具名对象参数 |
| 嵌套三元表达式 | 禁止 |

测试文件中的 `describe` 和 `it` 回调天然较长、嵌套较深，因此 `tests/` 不检查函数行数和回调嵌套层数，其余上限照常适用。

超过上限时，按职责拆分，而不是按行数机械切开：

- 主进程入口只负责装配，窗口、IPC、运行时生命周期和退出清理各自成模块；验收代码放在 `src/main/verification/`。
- React 组件超过上限时，先把状态逻辑提取成 hook，再把可独立理解的区域提取成子组件。
- 解析校验和业务逻辑分开：先把外部输入转换成可信类型，后续代码只处理可信类型。

## 命名

- 使用完整的英文单词，不自造缩写；通用缩写（`id`、`url`、`ipc`、`pty`）除外。
- 布尔值使用 `is`、`has`、`can`、`should` 等前缀。
- 函数名以动词开头，说明它做什么；只做转换或读取的函数，避免使用暗示副作用的名字。
- 同一概念在主进程、后台和 renderer 中使用同一个名字。

## 注释

注释的读者是下一个维护者。代码说明“做了什么”，注释说明代码自身表达不出来的东西：为什么这样做、调用方必须遵守什么、出错和取消时会怎样。

### 必须写的注释

1. **文件头**：说明模块职责、运行在哪个进程（主进程、后台、preload、renderer），以及它拥有并负责释放的资源。

   ```ts
   /**
    * 项目任务控制器：在主进程中保存项目脚本任务，并把运行状态推送给 renderer。
    * 拥有每个运行中任务的终端子进程；窗口关闭或应用退出时由 dispose() 统一终止。
    */
   ```

2. **每个导出声明**：中文 JSDoc。写清楚它做什么；有下列情况时也必须写明：
   - 参数有非显然的约束
   - 返回值有特殊含义
   - 会抛出错误
   - 有副作用（文件、子进程、IPC、全局状态）
   - 有调用方负责的清理

   ```ts
   /**
    * 将应用自带核心安装到 MyDSH 独立目录，不访问网络。
    * 调用方必须先取得应用单实例锁，并在本函数完成后才启动 Runtime。
    * @throws 清单校验失败或文件摘要不符时抛出；已安装的旧核心保持不变。
    */
   ```

3. **行内注释**：只用来解释下列原因：
   - 平台差异：macOS 与 Windows 行为不同的地方
   - 顺序和竞态约束：为什么必须先做 A 再做 B，为什么这里要等待
   - 安全校验：为什么要复核发送方、为什么拒绝某类输入
   - 魔法数字：数值的来源和取舍
   - 临时绕过：绕开的是什么问题，满足什么条件后可以移除

### 不要写的注释

- 复述代码的注释，例如在 `count += 1` 上方写“计数加一”。
- 注释掉的代码。不需要的代码直接删除，历史由 Git 保存。
- 修改历史、作者或日期。这些信息属于提交记录。
- 未归属的临时事项标记。

### 参照范例

同仓库的上游模块注释质量较高，可以参照它们的写法：

- `packages/jobs/jobs/src/index.ts`：接口契约、取消与清理语义
- `packages/shell/bash-local/src/index.ts`：进程生命周期与平台差异

MyDSH 自有代码的注释使用简体中文；标识符、协议字段和第三方专名保持原有写法。

## 错误处理与输入校验

- 来自 IPC、Remote、文件和网络的输入一律视为不可信，在边界处校验一次，转换成可信类型后再往里传。
- 通用的校验工具放在 `src/shared/validation.ts`，不要在每个文件里重新定义 `isRecord` 一类的函数。
  - preload 是独立的 CommonJS 脚本，独立工作区包有自己的构建，它们无法引用 `src/shared`。这两类文件可以保留自己的副本，但要在副本旁注明原因。
- 错误信息使用中文，说明发生了什么、用户或调用方可以怎么做；不要把凭据、令牌等敏感内容写进错误信息和日志。
- 失败路径和清理路径与正常路径同样重要：取消、超时、进程退出和窗口关闭时，资源必须由明确的所有者释放。

## 改动方式

- 重构与行为修改分开提交。重构提交不改变行为；重构中发现的缺陷单独提交，并补充测试。
- 纯格式化的提交登记在 `.git-blame-ignore-revs` 中，避免影响 `git blame`。
- 提交保持小而完整，每个提交都能单独通过 `pnpm run check`。
